Agentic Canvas — Two On-device AI Agents

Both agents run 100% locally via Ollama — no API keys, no data leaves the machine.

Agent 1 — Column Mapper gemma4:e4b (~4B, fast)
TriggerUser uploads CSV/Excel with unknown columns
TaskReads raw header + sample rows → proposes mapping to canonical schema (customer_id, order_date, unit_price…)
GuardrailsMultilingual heuristic fallback if LLM unavailable; human confirms before pipeline runs
OutputJSON column mapping saved to config/segsmart.json
Agent 2 — Campaign Copywriter qwen3.6:35b (MoE, quality)
TriggerSegmentation complete → 5 named segments ready
TaskWrites one campaign card per segment: objective, channel, offer, headline, rationale
GuardrailsNumbers computed in Python — never by LLM; discounts set by owner only; rule-based fallback always on
OutputCampaign cards → owner approves → mailing artifact + webhook
Key principle: LLMs write copy, never commerce. Revenue estimates, discount values, and voucher codes always come from deterministic Python or the shop owner — never from the model.

Feature Engineering  seg/features.py

Per-customer features collapse transaction history into a segmentation-ready matrix.

RFM Core Features
Recency Days since last order (snapshot − last_seen)
Frequency Count of unique orders per customer
Monetary Total lifetime spend (sum of line_value)
→ Quintile-scored 1–5, tie-aware  |  R score reversed (recent = 5)
def _score(series, reverse=False):
  # tie-aware: equal values → same score
  pct = series.rank(pct=True, method="average")
  q = np.ceil(pct * 5).clip(1, 5)
  return (6 - q) if reverse else q

Journey & Key Trials
1
Short real export → flat results
Real 2-month e-shop export: ARI ≈ 0.06, silhouette ≈ 0.04. RFM collapsed — everyone had ~1 order. Frequency and monetary were near-identical across all customers. Pipeline correctly warned us instead of inventing segments. Finding: data window matters as much as the algorithm.
2
Synthetic data breakthrough
Built gen/synth.py — 500 customer archetypes (Champion, Loyal, B2B, New, At-risk, Dormant), 20-month window, Czech seasonality, Christmas peak. Result: silhouette 0.49, ARI 0.49. Real-vs-synthetic contrast became a key finding: you need history, not just data.
3
LLM hallucinated discount codes
qwen3 invented voucher codes ("JARO15", "SAVE20") and specific % discounts that no real shop accepted. Solution: prompt guardrails + strip_voucher_codes() regex + has_invented_discount() fallback to rule-based copy. Trust but verify — all model output is sanitized.
4
Data ingestion chaos
Real e-shop CSV: Czech decimal comma, billing/shipping structural rows, cancelled orders, missing order IDs, cp1250 encoding. Each case explicitly handled in loader.py. Contract enforced: 12 hostile test fixtures must all produce identical output.

Models & Algorithms

Two complementary algorithms — interpretability vs. discovery — validated by their agreement.

① RFM Quantile Scoring
RolePrimary segmentation — the product's default
MethodQuintile scoring (1–5) on R, F, M independently
Tie-awareEqual values always get same score (rank pct)
Output5 named: Champions, Loyal, At-risk, New, Dormant
StrengthInterpretable — owner can read WHY a customer is "At-risk"
WeaknessPre-defined thresholds, may miss real cluster geometry
② KMeans Clustering
RoleUnsupervised cross-check of RFM results
MethodKMeans k=5 on log-scaled, z-scored features
Featuresrecency, frequency, monetary, AOV, basket, products
Adaptsk auto-reduced for small datasets (k < n)
StrengthFinds real geometry in data, no pre-set assumptions
WeaknessLabels meaningless without RFM interpretation layer

Validation of Results

Multi-layered validation: statistical metrics, data honesty checks, and executable tests.

Statistical Metrics
  • Silhouette Score: 0.49 on 20-month synthetic (good cluster separation) · 0.04 on 2-month real (system warns)
  • Adjusted Rand Index (RFM ↔ KMeans): 0.49 synthetic / 0.06 real — the honesty metric shown on dashboard
  • Segment profiles: customers %, revenue % per segment — deterministic, reproducible
Data Honesty Layer
  • Ingest report: rows kept / dropped per category (date parse fails, missing customer, cancellations, non-positive prices)
  • Quality warnings auto-triggered: window < 6 months · median price < 1 (wrong decimal) · < 50 customers · ARI ≈ 0
  • Impact estimates always deterministic Python (response-rate table), never LLM-generated
Test Suite — ~115 pytest cases, all offline
  • tests/test_messy.py: 12 hostile CSV formats (cp1250, BOM, no order IDs, Excel serials, ambiguous dates…) → must all produce identical numbers
  • tests/test_no_pii.py: SHA-256 denylist of personal names, e-mail patterns, private artifacts never git-tracked
  • Regression tests: tie-aware scoring, C-invoice rule, auth, read-only guards
  • CI runs full suite on every push; Docker image published on version tags
Areas of Improvement

Honest assessment of what the current alpha does not yet do well.

Prediction vs. Description
The tool is purely descriptive (RFM) + cross-validated (KMeans). No churn/propensity model predicts which customers will leave next. Adding a supervised churn predictor per segment is the highest-value next ML step.
Short Data Window Problem
2 months of real data = meaningless segmentation (ARI 0.06). The system warns — but SMEs with new shops have no fix. Future: cold-start heuristics, cohort-based approach for short histories.
LLM Output Quality
Despite guardrails, qwen3.6 occasionally produces generic copy. Prompt engineering, fine-tuning on e-commerce data, or few-shot examples from real campaigns would significantly improve output quality.
No A/B Testing Loop
Campaign impact estimates use a static response-rate table. No feedback loop from actual open/click rates back into the model to calibrate estimates over time.
Margin-Blind Segmentation
Segmentation is revenue-based, not profit-based. Heavy discount users appear as Champions. Margin data from ERP/accounting would fix this — but most SMEs don't export it.
Single-server Scale Limits
stdlib HTTP + synchronous pipeline. Slow quality-model run blocks the dashboard. No background job queue, no horizontal scaling. Appropriate for one SME, not a multi-tenant product.
Next Steps

Three horizons: short-term polish → medium-term ML expansion → long-term productisation.

Short-term (1–3 months)
  • Scheduled refresh (cron/systemd → pipeline.py --config)
  • BigQuery & Shoptet connectors hardened for live tenants
  • Background job queue — quality model doesn't block HTTP
  • Native ESP integrations (Ecomail / SmartEmailing / Mailchimp)
Medium-term (3–9 months)
  • Churn / propensity model per segment
  • Margin-aware segmentation (profit not revenue)
  • A/B testing engine — split offers across sub-groups
  • Managed SaaS option with zero-knowledge architecture
Long-term (9+ months)
  • CLV (Customer Lifetime Value) prediction model
  • Attribution modelling — link campaigns to revenue lift
  • Multi-shop / franchise mode with PII separation
  • Open ecosystem: connector SDK + community adapters
